# 流程与主链约束

这份文档只做两件事：

1. 把 `research-intel` 当前代码里的真实运行流程讲清楚。
2. 把后续收敛时必须遵守的主链约束写死，避免继续长成多入口、多语义、多残留的拼装系统。

本文档故意把 `当前现状` 和 `目标设计` 分开写。前者描述今天代码实际上怎么跑；后者描述接下来应该收敛成什么样。

## 适用范围

- 只处理 `research-intel`
- 运行与部署真相：`baohe:/root/projects/research-intel`
- GitHub 同步目标：`https://github.com/cnfjlhj/research-intel`
- 本地仓库主要用于开发、审查、验证；不应再和 `baohe` 形成长期漂移

## 当前现状

### 1. 入口面

当前代码里有三类入口：

- `cron -> scripts/research-intel/run-daily.sh`
- `Web -> POST /research-intel/actions/run`
- `scheduler-loop.js -> codex-supervisor.js / verify-daily.js`

这三类入口最后都会汇到同一条运行主链，但它们的触发语义和成功反馈并不完全一致。

## 当前不合理点

下面这些不是猜想，而是当前设计层面已经能直接看出来的异味：

### 1. 入口过多

现在有 cron、Web 手动触发、scheduler loop 三个入口。

问题不是“能不能跑”，而是：

- 同一件事有多个入口，运行语义更难统一
- 出错时更难判断到底是哪一层返回了“成功”
- 容易继续长出额外的分支逻辑和补丁语义

### 2. `codex-supervisor` 和 `daily-run.js` 是双层编排

当前不是一个单层清晰流水线，而是：

- supervisor 负责 date-scoped worker、prompt、tmux、heartbeat
- worker 默认会执行一条具体的日级流水线；当前 prompt 明确允许并鼓励直接调用 `daily-run.js`
- `daily-run.js` 再对子论文起 paper-scoped tmux session

这条链可以工作，但阅读和排障成本高，架构观感容易显得拼装。

### 3. Web 的“触发成功”语义仍然偏松

从代码结构上看，Web 的职责更像“发起一个后台动作”，而不是“确认新 run 已经真实启动并进入稳定阶段”。

如果这层不收紧，就会出现：

- 页面说“已触发”
- 但 supervisor 实际没启动新一轮
- 或 worker 已经进入异常状态而 UI 仍给乐观反馈

### 4. `stale` 语义容易和“可再次触发”混在一起

`stale` 同时带有两种含义：

- 这个 run 没有继续推进
- 这个 session 可能还活着

如果不把这两件事拆开，控制台、supervisor、排障脚本就容易各自解释一套。

### 5. 日级重跑动作过重

`daily-run.js` 当前会先删掉当天 `work/` 和 `records/` 的日目录再重建。

这对“第一次跑”没问题，但对下面几类操作不友好：

- 补跑
- 局部修复
- 审计昨天到底生成了什么
- 比较前后两次 run 的差异

### 6. 工作态与发布态分成两棵大树，收益和成本都很高

`work/` 与 `research-intel-records/` 分离有其合理性，但现在的目录负担已经不轻：

- 好处是调试和持久化职责分离
- 代价是清理、同步、部署、Git 边界都更容易乱

这个分层本身不一定要推翻，但必须有更严格的保留规则与同步规则。

## 目标设计

目标不是大改所有实现，而是把系统收敛成一条更像主系统、而不是补丁堆叠的主链。

### 1. 目标原则

- 只保留一条默认主链
- 所有入口共享同一套触发语义
- `paper.pdf` 永远是单篇生成的唯一真相源
- 每篇论文都必须是独立 paper scope、独立 tmux session
- 成功必须由关键产物和校验结果定义，而不是由“命令发出去了”定义
- 清理、同步、部署都要先分清工作态、缓存态、持久态

### 2. 目标主链图

```text
                         +----------------+-----------------+
                                          |
                 +------------------------+------------------------+
                 |                         |                        |
                 v                         v                        v
          cron trigger              web trigger              manual cli trigger
                 \_____________________|___________________________/
                                      |
                                      v
                         +----------------------------------+
                         | daily pipeline                   |
                         | - candidate discovery            |
                         | - scoring / selection            |
                         | - per-paper artifact generation  |
                         | - daily curation                 |
                         | - publish                        |
                         | - delivery verify                |
                         +----------------+-----------------+
                                          |
                                          v
                         +----------------------------------+
                         | per-paper runner                 |
                         | one paper -> one workspace       |
                         | one paper -> one tmux session    |
                         | one paper -> validated HTML      |
                         +----------------+-----------------+
                                          |
                                          v
                         +----------------------------------+
                         | publish contract                 |
                         | 必须同时满足：                   |
                         | - index.html                     |

                                          v
                         +----------------------------------+

                         | 可读、可审计、可补发             |

```

### 3. 目标阅读上下文模型

目标不是让多篇论文共享一个脏 session，而是让每篇论文在独立 session 中，按受控方式继承一小部分前序阅读结论。

这里采用：

- `分层上下文`
- `局部依赖图`

不采用：

- 所有论文直接共享一个 session
- 把前面 session 的原始聊天记录整坨塞给后面的论文

#### 3.1 三层上下文

```text
layer 0: global context
  - research_brief.md
  - method_tree.md / method_tree.json
  - daily reading_route.md
  - 当天的主题、术语、主线问题

layer 1: local dependency graph
  - 只选择与当前论文最相关的前序论文
  - 每个前序节点只提供结构化 dependency card
  - 内容只包含已确认的定义、差异点、未解决问题、比较重点

layer 2: current paper source of truth
  - current paper.pdf
  - current paper_meta.json
  - current evidence pages
  - current openreview / web coverage
```

原则是：

- 第 0 层负责告诉系统“今天在研究什么”
- 第 1 层负责告诉系统“读到这篇时，前面哪些结论值得带上”
- 第 2 层负责告诉系统“当前论文真正说了什么”

其中第 2 层始终优先级最高，不能被前两层覆盖。

#### 3.2 局部依赖图主链

```text
selected papers
      |
      v
+------------------------------+
| build reading order          |
| 先确定 1..N 的阅读顺序         |
+---------------+--------------+
                |
                v
for paper_i
    |
    v
+-----------------------------------------------+
| find local dependencies among prior papers    |
| 只允许从 paper_1 ... paper_(i-1) 中选          |
| 选择最相关的 0..K 篇，形成 backward-only DAG   |
+----------------------+------------------------+
                       |
                       v
+-----------------------------------------------+
| build session context package                 |
| = layer 0 global context                      |
| + layer 1 dependency cards                    |
| + layer 2 current paper.pdf                   |
+----------------------+------------------------+
                       |
                       v
+-----------------------------------------------+
| run isolated paper-scoped Codex session       |
| 当前论文独立生成 index.html / paper_card.json  |
+----------------------+------------------------+
                       |
                       v
+-----------------------------------------------+
| emit current dependency card                  |
| 给后续论文使用，但不是原始聊天记录             |
+-----------------------------------------------+
```

#### 3.3 局部依赖图的硬约束

- 只允许依赖阅读顺序中更早的论文，不允许前向依赖。
- 默认只允许小扇入。
  - 建议 `K <= 3`
- 依赖边必须是“结构化卡片”，不能是 session transcript。
- dependency card 只写压缩后的语义，不写冗长过程性推理。
- 当前论文若与前序论文冲突，必须以 `paper.pdf` 为准，并在产物里显式指出冲突。
- 依赖图的目标是帮助比较和衔接，不是替代当前论文的独立阅读。

#### 3.4 每篇论文建议注入的 dependency card 字段

```text
- paper_id
- title
- why_relevant_to_current
- confirmed_definitions
- confirmed_method_claims
- unresolved_questions
- compare_axes
- caution_points
```

可以把它理解为：

- 不是“上一篇论文聊了什么”
- 而是“上一篇论文里哪些已确认内容，对当前这篇有用”

#### 3.5 这个设计借鉴了什么

这部分借鉴的是一类更克制的研究工作流设计，而不是照搬具体实现：

- 借鉴“中间语义层”
  - 先产出 `reading_route`、`dependency_card` 这类可审计文件，再进入下一篇论文
- 借鉴“上下文自动装配”
  - 后续 session 读取结构化前序产物，而不是共享原始上下文
- 借鉴“组合式工作流”
  - 候选发现、阅读排序、单篇生成、依赖卡片沉淀是明确分段的

不借鉴的部分是：

- 跨论文直接共享一个长 session
- 用过程性聊天记录作为长期主数据

#### 3.6 必须前置 route planning

如果系统要支持“局部依赖图”，那阅读顺序就不能在所有单篇论文都生成完之后才最终决定。

目标流程里应当变成：

```text
candidate discovery
      |
      v
preliminary selection
      |
      v
route planning
  - 先产出稳定的 1..N 顺序
  - 先写出 route logic
  - 先确定哪些论文更像 prerequisite / contrast / extension
      |
      v
per-paper generation in route order
      |
      v
emit dependency cards and local edges
      |
      v
final publish
```

也就是说，当前的 `reading_order.md` 不应该只是在所有东西都跑完以后做一个展示性总结；它在目标设计里应该上升成真正的前置运行输入。

#### 3.7 建议新增的中间文件

为了避免“上下文依赖”再次变成隐性状态，目标设计建议把这些文件显式落盘：

```text
work/research-intel/daily/<date>/
  reading_route.json
  reading_route.md
  dependency_graph.json
  dependency_cards/
    01-paper-a.json
    02-paper-b.json
    ...
  session_contexts/
    01-paper-a.json
    02-paper-b.json
    ...

research-intel-records/daily/<date>/
  reading_route.json
  reading_route.md
  dependency_graph.json
  dependency_cards/
    01-paper-a.json
    02-paper-b.json
    ...
  session_contexts/
    01-paper-a.json
    02-paper-b.json
    ...
```

它们的职责分别是：

- `reading_route.json`
  - 机器主读版本
  - 定义稳定顺序、阶段角色、阅读路线和预期比较轴
- `reading_route.md`
  - 人类可读版本
  - 给 Web、README 展示和人工审阅用
- `dependency_graph.json`
  - 记录局部依赖边
  - 明确每条边为什么存在
- `dependency_cards/*.json`
  - 每篇论文生成后写出的结构化摘要卡
  - 供后续论文复用
- `session_contexts/*.json`
  - 每篇论文启动前实际装配出来的上下文包
  - 用来审计“这篇到底带了哪些前文”

#### 3.7.1 保留策略

这部分当前先定成：

- `完整双写`
  - `work/` 保留完整副本
  - `research-intel-records/` 也保留完整副本

采用这个策略的原因是：

- 便于审计
- 便于回放
- 便于之后脱离工作目录单独检查当日阅读链
- 不把“真正用过的上下文”只留在瞬时工作区

但这里的“完整双写”当前只明确适用于：

- `reading_route.*`
- `dependency_graph.json`
- `dependency_cards/*.json`
- `session_contexts/*.json`

这一步暂时不自动扩展到所有大二进制，例如：

- `paper.pdf`
- 页面截图
- 大体积中间缓存

这些重资产是否也要在 `records/` 再复制一份，后续单独决策，不在本轮设计里顺手放大范围。

#### 3.9 建议的选边规则

局部依赖图不需要很复杂，但必须足够稳定、可解释。

建议规则：

1. 只从更早的论文里选边。
2. 默认最多 3 条入边。
3. 优先级从高到低：
   - 同 branch 且方法机制明显相关
   - 核心问题定义高度重合
   - 明确形成“对照/替代/扩展”关系
   - 在 `compare_axes` 上有直接可比性
4. 如果候选过多，优先保留多样角色：
   - 1 条 prerequisite
   - 1 条 same-branch extension
   - 1 条 contrast
5. 如果没有明显相关前序论文，允许 0 条依赖边。

目标是让依赖图帮助阅读，而不是为了图结构而强行连边。

```text
      v
publish final daily records
```

这比“所有论文独立但彼此无关”更有阅读逻辑，也比“共享一整个大上下文”更稳。

### 4. 目标职责边界

- `trigger layer`
  - 只负责提出“我要跑今天这一轮”
  - 不负责宣称运行成功
- `run gateway`
  - 负责加锁、preflight、状态机推进、统一返回值
- `daily pipeline`
  - 负责日级候选发现、筛选、汇总、发布
- `per-paper runner`
  - 只负责单篇论文从 `paper.pdf` 走到已校验 `index.html`
- `publish contract`
  - 只认关键产物，不认口头状态

## 后续改造必须遵守的约束

### 1. 不再增加新的运行模式

- 不新增“临时 fallback 模式”
- 不新增“内部特供分支路径”
- 不新增“另一套半自动入口”

如果需要实验新思路，必须在同一主链下替换组件，而不是再开一条隐性旁路。

### 2. 不再把辅助信息当主输入

以下都只能做辅助：

- 抽取文本
- 页面图片
- OpenReview
- 中文 blog
- 代码仓

真正的单篇生成真相来源只能是 `paper.pdf`。

### 3. 不再共享跨论文上下文

- 每篇论文一个工作目录
- 每篇论文一个 tmux session
- 每次 fresh attempt 单独落到 `generation_attempts/attempt-XX/`

不能再出现“上一篇论文的上下文或修补痕迹影响下一篇”的设计。

### 4. 不再用模糊状态词充当验收

以下不能单独代表完成：

- 已触发
- 已提交
- worker 在跑
- tmux 还活着
- 页面能打开

只有关键产物存在且校验通过，才算单篇论文完成；只有日报与投递状态齐全，才算日级 run 完成。

### 5. 清理必须先分类，再删除

未来清理会按三类来做：

- 持久态
  - 不能直接删，如 `research-intel-records/`
- 工作态
  - 可按规则清理，但需要保留当前活动 run
- 缓存态 / 临时态
  - 可批量清理，如大部分 `/tmp/research-intel*`

不能在没有清理白名单和排除规则前做粗暴删除。
